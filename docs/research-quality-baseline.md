# 조사 품질 개선 전 평가

기준 커밋: `3ba50e8`. 2026-10-08에 기존 실제 답변 네 개를 사람이 다시 평가했다. 새로운 모델 실행이나 자동 채점 결과가 아니다.

## 무엇을 개선하려는가

답변을 저장하는 것과 충분한 답변을 만드는 것은 다르다. 현재는 질문의 조건이 빠지거나 근거가 부족해도 응답을 받으면 그대로 저장된다. 다음 개선은 이런 문제를 발견하고 필요한 부분만 보완하는 과정이다. 에이전트 수는 아직 결정하지 않았다.

## 공통 평가 기준

- 질문에서 요구한 각 조건에 답했는가?
- 결론에 영향을 주는 전제와 예외를 설명했는가?
- 기술적 주장 바로 뒤에 해당 공식 문서 링크가 있는가?
- 조사 과정의 본문 열람을 독립적으로 확인할 기록이 있는가?
- 문서의 사실과 설계 제안·추론을 구분했는가?
- 읽는 사람이 용어를 다시 검색하지 않고 결론과 조건을 이해할 수 있는가?

판정은 충족, 보완 필요, 기록 부족, 미평가로 나눈다. 응답 수신 상태인 needs_review는 품질 합격이 아니다. 읽기 쉬운지는 사용자 확인이 필요하다.

## 기존 답변에서 발견한 문제

| 사례 | 핵심 질문에 대한 답 | 보완할 내용 | 본문 열람 증거 |
| --- | --- | --- | --- |
| TaskGroup과 gather 비교 | 핵심 차이는 설명함 | return_exceptions=True의 대기 범위가 명시되지 않음. 결론과 한계의 일부 주장에 바로 뒤 링크가 없음 | 기록 부족 |
| 접근 실패 후 TaskGroup 조사 | 실패 후 대체 검색을 계속하고 답함 | ExceptionGroup이라는 일반화를 ValueError만 발생한 경우로 한정할 필요 | 기록 부족 |
| Slack 게시 권한 | 참여·미참여 채널의 권한을 구분함 | 최소 권한 제안의 일부에 바로 뒤 근거 링크가 없음 | 기록 부족 |
| Slack 성공 판단 | API 성공·게시·읽음을 구분함 | 응답 없는 타임아웃의 결과 불명확성과 중복 통제의 구현 조건을 더 명확히 설명할 필요 | 기록 부족 |

위 보완 필요 사항을 모두 잘못된 답변으로 취급하지 않는다. 누락, 조건의 일반화, 근거 연결, 기록 부족을 구분한다. Slack 성공 판단 예시에는 사후 검토 메모가 있으므로 원래 답변과 검토 메모도 구분한다.

사용자는 답변이 어렵고 눈에 잘 들어오지 않는다고 피드백했다. 네 답변 각각의 이해도나 개선 후 이해도는 아직 측정하지 않았다.

## 같은 조건으로 다시 평가할 질문

기존 예시의 질문과 허용 도메인을 그대로 사용한다. 원래 답변은 비교 기준으로 보존한다.

- [비교 질문](examples/taskgroup-vs-gather.md): 나머지 작업 처리, 예외 전달, 설정별 대기를 확인한다.
- [접근 실패 질문](examples/taskgroup-alternative-document.md): 실패한 문서를 근거로 쓰지 않고 대체 검색을 계속하는지 확인한다.
- [권한 질문](examples/slack-posting-permissions.md): 채널 참여 조건과 제안의 적용 범위를 확인한다.
- [성공 판단 질문](examples/slack-posting-verification.md): 응답 성공·게시·읽음을 구분하는지 확인한다.

기존 예시에만 맞춘 개선을 피하기 위해 다음 질문도 추가한다. 아직 실행하지 않았으며, 기대하는 동작을 실제 관찰한 결과로 기록하지 않는다.

| 새 질문 | 확인할 문제 | 기대하는 동작 |
| --- | --- | --- |
| Python 3.10에서 TaskGroup을 사용하는 방법은? | 잘못된 전제를 받아들이는가 | 추가된 버전을 확인하고 해당 버전에서는 사용할 수 없음을 설명 |
| chat.postMessage가 타임아웃됐다. 미게시로 판단하고 바로 재전송해도 되는가? | 응답이 없다는 사실과 게시 실패를 혼동하는가 | 게시 결과가 불명확하다고 설명하고 중복 가능성과 확인·재시도 방안을 구분 |
| message 이벤트로 채널의 모든 사람이 읽었는지 확인하는 방법은? | 근거 없는 기능을 만들어내는가 | 이벤트가 보여주는 범위를 확인하고 전체 사용자의 읽음을 증명할 수 없음을 설명 |

## 다음 구현에서 확인할 것

1. 질문의 필수 쟁점과 답변 내용을 대응시킨다.
2. 주장과 원문 근거를 대응시키고, 열람 실패나 증거 부족을 드러낸다.
3. 부족한 쟁점만 재조사하고 횟수·시간·비용의 한도에서 종료한다.
4. 확인 불가능한 결과를 확인 완료로 표시하지 않고 사람에게 판단을 넘긴다.
5. 최종 답변을 쉽게 쓰되 조건과 예외를 생략하지 않는다.

검토 역할이 같은 답변을 읽고 동의하는 것만으로 원문 검증이 되지는 않는다. 조사와 검증을 별도 에이전트로 나눌지는 필요한 정보와 실패 원인을 확인한 뒤 결정한다.

## 개선 효과를 확인하는 방법

같은 질문·허용 도메인·모델 설정으로 개선 전후를 비교하고 실행 조건을 기록한다. 한 번의 좋은 답변으로 안정적인 향상을 주장하지 않는다.

- 필수 쟁점 누락, 잘못된 전제 수용, 근거 없는 단정의 건수를 기록한다.
- 본문 열람 증거 부족은 내용 오류나 접근 실패와 별도로 기록한다.
- 재조사로 해결한 문제와 남은 문제를 추적한다.
- 실행 시간, 사용량, 재시도 횟수도 비교한다.
- 읽기 쉬운지는 사용자가 결론과 조건을 이해하는지 확인한다.

현재 완료한 것은 평가 기준과 기존 답변의 기준점 정리다. 검증·재조사 기능과 개선 후 결과는 아직 구현하거나 검증하지 않았다.
