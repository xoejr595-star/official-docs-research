# 관찰을 근거로 발전시키기

순서는 고정 일정이 아니다. 실제 필요가 확인된 항목만 구현한다.

| 실제로 관찰할 문제 | 다음 최소 변경 후보 | 재검증 |
| --- | --- | --- |
| 원문이 뒷받침하지 않는 주장을 작성 | Reviewer 분리 | 동일 질문·원문으로 잘못된 주장 검출 여부 비교 |
| 근거 부족을 찾아도 답변을 끝냄 | 횟수가 제한된 재조사 분기 | 실패 질문에서 추가 근거 확보와 중단 조건 확인 |
| 출력 형식 차이로 후속 처리가 실패 | 답변 structured output | 필수 필드와 실패 상태 처리 확인 |
| 실행 환경 종속·도구 통제 한계가 실제 사용을 막음 | 모델/검색 API 직접 연결 | 같은 입력·출처와 오류 처리 비교 |
| 다른 PC에서 실행 환경 재현 실패 | Docker | 새 환경에서 같은 명령으로 실행 |

커밋은 `관찰한 문제 → 원인 가설 → 변경 이유 → 검증 결과`로 설명한다.
한 번에 여러 개선을 넣거나 일부러 실패를 만들지 않는다. 코드가 잘못했다는 증거와 실행 환경 제약을 구분한다.

포트폴리오 설명 원칙:

> 에이전트 숫자가 아니라, 사용자의 질문에서 공식 문서 검색·본문 확인·한국어 답변·파일 저장까지 어떤 반복 업무를 연결했는지 설명한다. 실제로 검증한 범위와 사람에게 남은 확인 작업을 밝힌다.

향후 면접에서 sub-agent는 독립 작업 위임, agentic workflow는 모델 판단이 개입하는 작업 흐름, harness는 실행·도구·기록을 지원하는 환경, skill은 재사용 가능한 작업 절차로 설명한다. 단순 조건 분기만 추가했다고 agentic이라고 주장하지 않는다.
